# 状态机与故障策略

## 正常路径

```text
HEALTHY
  ├─ 第一次探活失败 ──> SUSPECT
  └─ 用户改选具体节点 -> MANUAL_PROBATION

SUSPECT
  ├─ 探活恢复 ───────> HEALTHY（失败计数清零）
  └─ 同节点第二次失败 -> LOCAL_CHECK

LOCAL_CHECK
  ├─ 切换前复检恢复 ─> HEALTHY
  ├─ 本机直连离线 ───> LOCAL_OFFLINE
  └─ 本机可联网 ─────> CANDIDATE_SCAN

CANDIDATE_SCAN
  └─ 延迟前 3 名 ────> VALIDATING 1/3 -> 2/3 -> 3/3

VALIDATING
  ├─ 读满 1 MiB 且 >= 0.5 MiB/s -> HEALTHY
  ├─ 验证失败且本机在线 ────────> QUARANTINE -> 下一个候选
  └─ 验证失败且本机离线 ────────> LOCAL_OFFLINE（不隔离）
```

候选按延迟从低到高验证，采用第一个达到最低吞吐线的节点。目标是尽快恢复可用网络，而不是在故障期间做完整的性能排名。

## 四条恢复边

1. `SUSPECT -> HEALTHY`：下一轮探活成功立即清零，不把偶发抖动累计成故障。
2. `QUARANTINE -> 候选池`：TTL 到期自动解禁；重复隔离采用 10、20、40、80 分钟指数退避（上限 4 小时），24 小时没有新失败则清除历史。
   - 起始 TTL 取 10 分钟的依据：实测中静默挂死的节点可能在数分钟内自愈（一次实测里被隔离的节点 5 分钟后即恢复为全场最优），过长的首轮 TTL 会让可用节点长时间待在候选池外。
3. `LOCAL_OFFLINE -> LOCAL_CHECK`：到达复检时间后重新检查；本机离线期间绝不写隔离记录。
4. `MANUAL_PROBATION -> HEALTHY/SUSPECT`：用户选具体节点后按普通节点重新观察。用户选策略组则进入 `MANUAL_GROUP`，持续尊重手动选择。

## 兜底与恢复

当没有候选、延迟前 3 名都失败，或活跃隔离已达到 3 个时，脚本切到 `自动选择`：

- 兜底组存活：`URLTEST_FALLBACK`。
- 兜底组也无活节点：`OUTAGE`。
- `OUTAGE` 是唯一弹出 macOS 通知的状态；持续故障按 30 分钟限频。
- 两者都不是终态。脚本仍检查本机网络、清理过期隔离并扫描具体节点。
- 恢复扫描采用 2、4、8、16、30 分钟指数退避；有隔离更早到期时，会提前到该时间复检。

只有脚本自己切入兜底时才会自动离开。用户手动选中 `自动选择` 时，它属于 `MANUAL_GROUP`，脚本不接管。

## 手动选择与崩溃恢复

状态分别记录：

- `controller_selected`：脚本最后正式采用的选择。
- `manual_accepted`：最后认可的手动选择。
- `pending_from` / `pending_target`：PUT 前持久化的切换意图。

当前选择不等于当前期望选择时，视为用户或其他程序的改选。脚本自己的 PUT 若在完成后崩溃，下一轮会根据 `pending_*` 继续吞吐验证；不会未经验证直接宣布成功。

## 吞吐结果分类

| 状态 | 含义 |
| --- | --- |
| `PASS` | 读满 1 MiB，平均速度 >= 0.5 MiB/s |
| `LOW_THROUGHPUT` | 读满但低于阈值；0.3–0.5 MiB/s 会复测一次 |
| `TIMEOUT_PARTIAL` | curl 达到总超时，可能只读到部分数据 |
| `INCOMPLETE` | 请求正常结束，但没有读满 1 MiB |
| `HTTP_ERROR` | 测试服务器返回错误状态 |
| `PROXY_ERROR` | 代理连接、TLS、DNS 或 curl 执行失败 |

## 防抖与资源上限

- 同一节点连续 2 次失败才进入故障流程。
- 自动恢复动作至少间隔 60 秒。
- 候选延迟探测最多 10 个并发 worker。
- 只有故障时才做 1 MiB 吞吐验证，最多验证 3 个候选；正常巡检不产生测速流量。
- API 单响应不超过 4 MiB，日志最多 500 行，隔离状态最多读取 100 条。
